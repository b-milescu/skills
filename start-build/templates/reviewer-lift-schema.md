# Reviewer Lift Schema

Canonical schema for the builder-to-reviewer handoff block. This file owns the field names, row order, and required semantics. Authority claim/source shape and verification routing are canonical in `../../forge/reference/common-guard.md`. Review Packet templates and the Review Report carry generated-copy blocks from this schema so drift is detectable.

## Required fields

| Field | Required semantics |
|---|---|
| Reviewed SHA | MR head SHA at ready-marking; update on every post-ready push before asking for review. |
| Finding bindings | `none` when no report finding is in flight; otherwise every `MF-N`, `SF-N`, or `C-N` is serialized as `report=<stable report locator>; sha=<originating 40-hex reviewed SHA>; id=<short ID>` with multiple tuples separated by `<br>`. The originating report locator/SHA pair, not the current head alone, scopes the short ID. The cell carries that value alone, with no trailing prose, provenance, or explanation: the canonical validator reads any short ID mentioned in the cell as an in-flight binding, so a `none` cell that also cites `SF-1` provenance fails closed instead of parsing. Record issue/report provenance in the Review Packet body or another cell. Accepted spellings: the whole cell value may be bare or wrapped in **one surrounding code span**, because the canonical validator strips a single outer backtick pair — `` `none` `` and `none` are both valid, and the code-spanned form is this repo's fixture/test-pinned default (`tests/fixtures/finding-identities/reviewer-lift-valid.md`, `tests/finding-identity-bindings.mjs`). Backtick-wrapping individual `<br>`-separated tuples is **not** accepted; when a code span is used it surrounds the entire cell value. Before publication or ready transition validate all bindings against their reports with `node start-review/scripts/validate-finding-bindings.mjs` per [`start-review/reference/finding-identities.md`](../../start-review/reference/finding-identities.md); missing, stale, ambiguous, or contradictory bindings fail closed. |
| Review gate | `mandatory` unless a human explicitly bypassed the gate; for bypass use `bypassed (human override)` and record the reason in the MR. |
| Change tier | Declared effort-scaling tier for this change: exactly one of `trivial`, `moderate`, `high-risk` from the Change shape table in `docs/effort-scaling.md`, plus a one-clause rationale. Only discovery, packet, design, and verification depth scale with the tier; a `trivial` declaration never scales away the mandatory independent review gate or the exact-candidate local Check Gate. |
| Transport | Build-side transport evidence for the change-request mutations this builder performed (creation, description update, and the Draft-to-ready transition). Vocabulary matches `gitlab/reference/finish-result-schema.json`'s `transport` enum exactly: one of `mcp`, `glab-fallback`, `n/a`. Use `mcp` for GitLab MCP transport, `n/a` when no build-side mutation applies, and `glab-fallback` only with the eligible MCP gap named inline as `glab-fallback (gap: <named gap from gitlab/SKILL.md>)`, so an ineligible fallback is visibly unjustified in the durable artifact instead of knowable only from builder prose. Defaults to `mcp` when absent so already-published change requests do not fail closed. |
| Gate owner | `builder` or `parent`; names who owns the final local Check Gate evidence and Draft-to-ready transition. Parent-owned mode records `parent` plus the ownership contract from `start-build/reference/parent-owned-gate.md`; child builders hand off the candidate SHA and must not claim gate pass/fail. |
| Gate coverage | `exact-candidate-local`. `parent-owned` is not a coverage value; ownership is recorded in `Gate owner`. The full local Check Gate must cover the candidate used for ready/review. |
| Gate coverage rationale | Policy source, exact local gate command, candidate commit, and result. Parent-owned form: `Policy <ref>; command <cmd>; candidate <sha>; coverage exact-candidate-local; result: <not-run — parent-owned \| PASS — Gate Receipt <locator>>`. After every push, stale local gate, Gate Receipt, review, action, and reported CI pointers are invalid until rebound to the new `Reviewed SHA`. |
| CI pipeline | Advisory pipeline locator/ID, status, and commit SHA when available; use `N/A — <why>` when no CI exists or it is unavailable. Attribute a status to the candidate only when its commit SHA matches `Reviewed SHA` or a provider-proven integration candidate. Pending, failed, canceled, skipped, missing, stale, wrong-SHA, or unavailable CI never changes verdict or action eligibility. |
| Local gate | `PASS`, `FAIL`, `N/A`, or `not-run` plus the exact command. `PASS` on the exact candidate is the required quality gate. `N/A` requires a rationale that no local gate can run. In parent-owned mode use the ownership contract and exact-candidate Gate Receipt pointer from `start-build/reference/parent-owned-gate.md`; after the receipt the row carries exactly one literal `Gate Receipt` pointer (the label once, with one locator); child builders must not claim gate pass/fail. |
| RED | For behavior-touching implementation, failing command on the native test framework (`start-build/SKILL.md`) and expected failure reason from a TDD slice; use `N/A with rationale — <why>` for docs/config/mechanical/generated work, impossible TDD, or no native test framework; do not fake tests. |
| GREEN | For behavior-touching implementation, the same native test command passing and brief result; use `N/A with rationale — <why>` when RED is N/A or no test applies beyond the local gate; do not fake tests or meaningless checks. |
| Changed paths | Exact command `git diff --name-only <base>...HEAD` plus its measured output. Use the target branch as `<base>` and update after every push. This merge-base diff is authoritative; summing per-commit output is not equivalent. Any figure quoted in the MR body (including timings, counts, and sizes) must likewise be measured, not estimated. |
| Touched safety surfaces | Explicit `none`/`[]` or comma-separated bare tokens from `external-system`, `credentials`, `state`, `migration`, `gates`, `locks`, `deploy`, `wire-protocol`, `other`; `other` may carry a parenthetical annotation. The whole cell may use one surrounding code span, but individual list items must not be backtick-wrapped. |
| Acceptance surfaces | Comma-separated bare `surface:evidence` entries from `project_profile.acceptance_surfaces_ref`, or `none`/`[]`. With no ref, the fail-closed value is `none`. The whole cell may use one surrounding code span, but individual entries must not be backtick-wrapped. Evidence is `test`, `smoke`, `docs-read`, `ci`, or `N/A — <reason>`. |
| Decoupling proof | `single MR` for single-issue work (provider-neutral equivalents `single PR` and `single change request` are the same value, alone in the cell); otherwise list co-running change-request IDs, locators, or branches and summarize the Decoupling Contract check. |
| Reviewer Focus | Areas the reviewer should read hardest, or `none`. |
| Open Questions | `none` or a count/list of stable `OQ-N` IDs. |
| Approval authority | Approval policy claim for the provider approval side effect. Use `default-after-pass` when repo policy allows reviewer approval after a passing review unless an explicit restriction is present; use `restricted: <source/reason>` when approval is limited. Approval still requires review pass, exact reviewed SHA, exact-candidate local Gate Receipt, resolved blocking open questions, and the SHA-bound approval guard. The [Authority Verification](../../forge/reference/common-guard.md) seam owns the claim shape and restricted result. |
| Approval authority source | Verifiable source for the approval policy or restriction, such as `start-review/REVIEW-FLOW.md#approval-authority-policy`, project rulebook path+section, parent task prompt, or human/MR comment URL. It is separate from finish authority and grants no merge, auto-merge, release, deploy, or close authority. |
| Finish authority | Quoted finish-authority claim only; one of `none — requires explicit human/parent instruction`, `approval-only`, `reviewer may merge`, `queue auto-merge`, `human release`, or `project default: <policy>`. **Defaults to `none — requires explicit human/parent instruction`**; any granting value requires the affirmative quotable grant described in `Finish authority source`. The builder cannot grant authority; Authority Verification must verify it before finish routing. |
| Finish authority source | Verifiable source for the finish-authority claim, such as parent task prompt, human MR comment URL, rulebook path+section, or project default source. Required for every value; builder-provided text alone is not a grant. For any non-`none` value, the source must contain a quotable **affirmative grant** of the merge/auto-merge action. **Anti-pattern (fail closed, not a grant):** citing a setup/policy doc whose text says "these docs do not grant finish authority" (or is otherwise silent on merge/auto-merge) as the source for `reviewer may merge` / `queue auto-merge` / `project default` — a disclaiming or silent source forces the `none — requires explicit human/parent instruction` default. Authority Verification owns conflict handling and most-restrictive/no-action routing. The pure-local `validate_reviewer_lift` linter emits an **advisory** (warn-only, exit 0) diagnostic when a granting `Finish authority` value is paired with a source cell lacking a quotable affirmative grant; it never fails closed and never blocks ready/merge. |
| Delta since last ready push | `N/A before ready`; after any post-ready push, include old SHA → new SHA, reason, changed files, gate rerun, and whether the change is substantive. Every commit-bound pointer (`Reviewed SHA`, advisory CI pipeline observation, and in parent-owned mode the Gate Receipt pointer) is stale until rebound to the new SHA, per `start-build/reference/parent-owned-gate.md#stale-exact-sha-evidence-fails-closed-after-a-revision-push`. Refresh them before requesting re-review; do not duplicate the Gate Receipt body into the description. |

## Generated-copy contract

Approved generated copies live in `start-build/templates/review-packet.md`, `start-build/templates/review-packet-compact.md`, and `start-review/templates/review-report.md`, each delimited by the `REVIEWER-LIFT-SCHEMA` markers. Run `bash tests/reviewer-lift-schema.sh` after editing this schema or any copy; it verifies field order and flags unmarked stale duplicate field-list tables.
