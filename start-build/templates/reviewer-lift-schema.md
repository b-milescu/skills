# Reviewer Lift Schema

Canonical schema for the builder-to-reviewer handoff block. This file owns the field names, row order, and required semantics. Authority claim/source shape and verification routing are canonical in `../../forge/reference/common-guard.md`. Review Packet templates and the Review Report carry generated-copy blocks from this schema so drift is detectable.

## Required fields

| Field | Required semantics |
|---|---|
| Reviewed SHA | MR head SHA at ready-marking; update on every post-ready push before asking for review. |
| Finding bindings | `none` when no report finding is in flight; otherwise every `MF-N`, `SF-N`, or `C-N` is serialized as `report=<stable report locator>; sha=<originating 40-hex reviewed SHA>; id=<short ID>` with multiple tuples separated by `<br>`. The originating report locator/SHA pair, not the current head alone, scopes the short ID. Before publication or ready transition validate all bindings against their reports with `node start-review/scripts/validate-finding-bindings.mjs` per [`start-review/reference/finding-identities.md`](../../start-review/reference/finding-identities.md); missing, stale, ambiguous, or contradictory bindings fail closed. |
| Review gate | `mandatory` unless a human explicitly bypassed the gate; for bypass use `bypassed (human override)` and record the reason in the MR. |
| Transport | Build-side transport evidence for the change-request mutations this builder performed (creation, description update, and the Draft-to-ready transition). Vocabulary matches `gitlab/reference/finish-result-schema.json`'s `transport` enum exactly: one of `mcp`, `glab-fallback`, `n/a`. Use `mcp` for GitLab MCP transport, `n/a` when no build-side mutation applies, and `glab-fallback` only with the eligible MCP gap named inline as `glab-fallback (gap: <named gap from gitlab/SKILL.md>)` so an ineligible fallback is visibly unjustified in the durable artifact rather than knowable only from builder prose. This makes the MCP-first transport floor auditable, mirroring the finish-result schema's rule that transport evidence is recorded without trusting prose-only summaries. Optional field: it defaults to `mcp` when absent so already-published change requests do not fail closed. Whether this should instead be **required** (fails closed when absent, matching the finish-result precedent) is not decided here — the `start-build/templates/*` contract is published into target repos by `setup-dev-skills`, which owns the required-vs-optional decision (see Open Questions). |
| Gate owner | `builder` or `parent`; names who owns the final local Check Gate evidence and Draft-to-ready transition. Parent-owned mode records `parent` plus the ownership contract from `start-build/reference/parent-owned-gate.md`; child builders hand off the candidate SHA and must not claim gate pass/fail. |
| Gate coverage | `full-local`, `hybrid`, or `ci-only`. `parent-owned` is not a coverage value; ownership is recorded in `Gate owner`. `full-local` means the local Check Gate covers every required CI job, `hybrid` means local evidence covers only part of the required CI set, and `ci-only` means required checks must be proven by CI or an authorized CI waiver. |
| Gate coverage rationale | Policy source plus required CI mapping. Name the local gate command, required CI jobs, which jobs are locally covered, and any unmapped CI-only jobs or `none`. After every push, stale or wrong-SHA CI/local evidence is invalid until rebound to the new `Reviewed SHA`. |
| CI pipeline | Pipeline URL/ID, status, and commit SHA when available; use `N/A — <why>` when no CI exists or the pipeline is unavailable. The pipeline URL/ID and its bound commit SHA are **authoritative**; the recorded **status is an as-of-ready-marking snapshot**, not an authoritative claim, because with `full-local` coverage ready-marking does not wait for CI to go terminal. The finisher **must re-derive** the terminal CI status against the reviewed SHA before any finish action rather than trusting the recorded status — this re-derivation is a required step, not an optional habit. Green CI counts only when its SHA matches `Reviewed SHA`. This as-of framing sits beside the `Local gate` row's blocking rule, never in place of it: actual CI state at finish still gates eligibility. |
| Local gate | `PASS`, `FAIL`, `N/A`, or `not-run` plus the exact command. A completed local gate or parent-owned Gate Receipt permits review launch for every coverage class; `hybrid`/`ci-only` review may start while exact-SHA CI is pending. Failed, canceled, skipped, missing, stale, or wrong-SHA required CI blocks pass eligibility and every finish action unless an authorized CI waiver is recorded. In parent-owned gate mode use the ownership contract and Gate Receipt pointer from `start-build/reference/parent-owned-gate.md`; child builders must not claim gate pass/fail. |
| RED | For behavior-touching implementation, failing test/check command and expected failure reason from a TDD slice; use `N/A with rationale — <why>` for docs/config/mechanical/generated work or impossible TDD; do not fake tests. |
| GREEN | For behavior-touching implementation, passing test/check command and brief result; use `N/A with rationale — <why>` when no test applies beyond the local gate; do not fake tests or meaningless checks. |
| Changed paths | Exact command `git diff --name-only <base>...HEAD` plus its measured output. Use the target branch as `<base>` and update after every push. This merge-base diff is authoritative; summing per-commit output is not equivalent. Any figure quoted in the MR body (including timings, counts, and sizes) must likewise be measured, not estimated. |
| Touched safety surfaces | Explicit `none`/`[]` or comma-separated bare tokens from `external-system`, `credentials`, `state`, `migration`, `gates`, `locks`, `deploy`, `wire-protocol`, `other`; `other` may carry a parenthetical annotation. The whole cell may use one surrounding code span, but individual list items must not be backtick-wrapped. |
| Acceptance surfaces | Comma-separated bare `surface:evidence` entries from `project_profile.acceptance_surfaces_ref`, or `none`/`[]`. With no ref, the fail-closed value is `none`. The whole cell may use one surrounding code span, but individual entries must not be backtick-wrapped. Evidence is `test`, `smoke`, `docs-read`, `ci`, or `N/A — <reason>`. |
| Decoupling proof | `single MR` for single-issue work; otherwise list co-running MR IIDs/branches and summarize the Decoupling Contract check. |
| Reviewer Focus | Areas the reviewer should read hardest, or `none`. |
| Open Questions | `none` or a count/list of stable `OQ-N` IDs. |
| Approval authority | Approval policy claim for the provider approval side effect. Use `default-after-pass` when repo policy allows reviewer approval after a passing review unless an explicit restriction is present; use `restricted: <source/reason>` when approval is limited. Approval still requires review pass, exact reviewed SHA, pass-eligible CI/local-gate/OQ state, and the SHA-bound approval guard. The [Authority Verification](../../forge/reference/common-guard.md) seam owns the claim shape and restricted result. |
| Approval authority source | Verifiable source for the approval policy or restriction, such as `start-review/REVIEW-FLOW.md#approval-authority-policy`, project rulebook path+section, parent task prompt, or human/MR comment URL. This source is separate from finish authority and does not grant merge, auto-merge, release, deploy, or close authority. Authority Verification applies source precedence before approval. |
| Finish authority | Quoted finish-authority claim only; one of `none — requires explicit human/parent instruction`, `approval-only`, `reviewer may merge`, `queue auto-merge`, `human release`, or `project default: <policy>`. **Defaults to `none — requires explicit human/parent instruction`** — a finish-authority-granting value (`reviewer may merge`, `queue auto-merge`, or a `project default: <policy>` that grants merge/auto-merge) is allowed **only when an affirmative granting sentence is quotable in `Finish authority source`** (a rulebook section that *grants* merge/auto-merge, or a recorded human/parent instruction). `project default: <policy>` is valid **only when the cited rulebook section affirmatively grants** merge/auto-merge — not when it is silent on, or actively disclaims, finish authority. The builder cannot grant authority; Authority Verification must verify it before finish routing. |
| Finish authority source | Verifiable source for the finish-authority claim, such as parent task prompt, human MR comment URL, rulebook path+section, or project default source. Required for every value; builder-provided text alone is not a grant. For any non-`none` value, the source must contain a quotable **affirmative grant** of the merge/auto-merge action. **Anti-pattern (fail closed, not a grant):** citing a setup/policy doc whose text says "these docs do not grant finish authority" (or is otherwise silent on merge/auto-merge) as the source for `reviewer may merge` / `queue auto-merge` / `project default` — a disclaiming or silent source forces the `none — requires explicit human/parent instruction` default. Authority Verification owns conflict handling and most-restrictive/no-action routing. The pure-local `validate_reviewer_lift` linter emits an **advisory** (warn-only, exit 0) diagnostic when a granting `Finish authority` value is paired with a source cell lacking a quotable affirmative grant; it never fails closed and never blocks ready/merge. |
| Delta since last ready push | `N/A before ready`; after any post-ready push, include old SHA → new SHA, reason, changed files, gate rerun, and whether the change is substantive. Every exact-SHA pointer (`Reviewed SHA`, CI pipeline / `Gate coverage rationale` CI mapping, and in parent-owned mode the Gate Receipt pointer) is stale until rebound to the new SHA; a Gate Receipt tied to an older SHA is not gate evidence for the new reviewed SHA until a new exact-SHA Gate Receipt exists (see `start-build/reference/parent-owned-gate.md#stale-exact-sha-evidence-fails-closed-after-a-revision-push`). Refresh those pointers before requesting re-review; do not duplicate the Gate Receipt body into the description. |

## Generated-copy contract

Approved generated copies live in:

- `start-build/templates/review-packet.md` (`Reviewer Lift` block).
- `start-build/templates/review-packet-compact.md` (`Reviewer Lift` block).
- `start-review/templates/review-report.md` (`Reviewer Lift (builder handoff)` block).

Run `bash tests/reviewer-lift-schema.sh` after editing this schema or any approved copy. The check verifies field order against this file and flags unmarked stale duplicate field-list tables.
