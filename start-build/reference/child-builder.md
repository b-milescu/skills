# Child `change-builder` mode

Small, self-contained path for child builders delegated by a parent orchestrator. This file is the canonical owner of the child `change-builder` flow.

## Authority boundary

The launch prompt's `Gate owner` line is the **sole binding source** of the gate-ownership selection (`builder` = builder-owned gate, `parent` = parent-owned gate; when the line is absent the documented default is `builder`/builder-owned). The child must not infer gate ownership from "finish authority", forbidden-actions wording, or any other merge/finish-authority prose — those govern who may finish, not who runs the local gate, and must not influence the selection. Record `gate_owner_received` beside the Reviewer Lift in the durable Review Packet as specified by [../templates/builder-final-handoff.md](../templates/builder-final-handoff.md), not in the two-line final response. The parent compares that echo and Lift `Gate owner` against the launch selection/default; neither artifact grants ownership. The per-mode semantics stay owned by [parent-owned-gate.md](parent-owned-gate.md).

The child builder implements one work item and opens/maintains one Draft change request, marking ready only after the local gate is green or explicitly N/A with rationale. The parent orchestrator owns the mandatory review gate and any approval, finish, source-ref cleanup, or post-merge verification allowed by policy; the child must not start a reviewer, approve, finish, clean source refs, or claim the review gate is complete unless explicitly delegated.

Project-profile hooks may specialize project policy but must preserve the [Safety floors](../SAFETY.md#safety-floors).

Auxiliary project-index policy defaults to parent/coordinator ownership. Child worktrees treat index reports as read-only unless the project profile explicitly assigns index updates to the child, and child worktrees must not copy index artifacts between worktrees.

## Required reads

Load only the context needed for the work item: project rulebook index, `../SAFETY.md`, this child-builder path, `parent-owned-gate.md` when parent-owned gate mode is active, `issue-pickup.md`, `../templates/reviewer-lift-schema.md`, `../templates/builder-final-handoff.md`, linked change requests, and affected docs/source/tests. Use [context and planning](context-and-planning.md) for the Discovery Budget and Build Plan Packet. Open [implementation-flow.md](implementation-flow.md) only when the compact checklist below is insufficient or an edge case, revision, post-ready push, CI policy, or gate ambiguity requires the full common flow; leave parent reviewer discovery, reviewer launch protocol, finish action guidance, and post-merge verifier instructions unloaded unless the parent explicitly changes your scope.

## Absolute worktree paths for edits

The runtime's file read/write/edit tools resolve RELATIVE paths against the agent **session cwd** (the coordinator checkout), not a shell's `cd`. A `cd <worktree>` in a shell command does NOT relocate them: a child that `cd`s into its worktree and then edits with relative paths silently lands changes in the coordinator checkout, not its worktree.

For every file read/write/edit of a project file, use an ABSOLUTE path rooted in your worktree. Run git with `git -C <worktree>` rather than relying on shell cwd. Confirm edits land only in that worktree and preserve the coordinator checkout's pre-existing state, including unrelated dirt. The parent creates the worktree and passes its absolute path and source branch; reuse both verbatim for initial and revision runs under [source lifecycle](implementation-flow.md#source-lifecycle).

## Child checklist

Credential handling discipline applies before every local shell or provider step: never `cat`, `echo`, or otherwise print token-bearing config such as `.env`, provider CLI config files, PAT stores, token env vars, or any value that may contain a secret. If an explicitly approved command must consume a credential, read it into a shell variable inside that command without printing it, pass it directly to the consuming tool, and redact diagnostics as `[REDACTED]`.

1. Run `forge preflight` and verify selected-provider transport availability, checkout/repository binding, repository locator, and default branch.
2. Resolve the supplied work item, or use the issue-pickup flow when none was supplied. Follow the canonical [issue pickup flow](issue-pickup.md), including its required description-and-current-discussion read and contradiction handling, before planning or editing.
3. Follow [source lifecycle](implementation-flow.md#source-lifecycle): verify the allocated worktree is clean and bound to the assigned repository, branch, and current source head; reuse it without default-branch initialization. Re-read work-item/change-request state and ownership before editing. A revision also binds the existing change request and originating report/SHA/finding tuples; it does not change gate or finish ownership.
   Before planning/edits, follow [Task-selected specialists](context-and-planning.md#task-selected-specialists), including compact initial and revision runs.
4. Write a concise Build Plan Packet before edits: intended behavior, affected surfaces, test plan, risk, non-goals, and loaded context sources with relevance.
5. For a newly allocated source without a change request, push it and open its early Draft once with `forge publish`; on reuse/revision, update the existing change request instead. Include the provider-native work-item relationship/closure preview, a Review Packet, and the complete Reviewer Lift from `../templates/reviewer-lift-schema.md`. Fill `Approval authority` as `default-after-pass` with stable policy provenance unless an explicit restriction source applies. Fill the quoted `Finish authority` claim and verifiable `Finish authority source`; builders cannot grant authority.
6. Behavior-touching implementation follows TDD unless impossible or explicitly N/A with rationale in the change request. Runtime/operator/safety changes are examples of behavior-touching implementation, not a narrower TDD trigger. Exception categories require a recorded rationale and must not allow fake tests or meaningless checks. Work-item-driven work with sufficient acceptance criteria does not need a separate user-approval prompt before the first TDD slice. Missing or ambiguous behavior scope still routes back to triage with exact unanswered questions. For docs/config/mechanical work, record `TDD: N/A` rationale instead of faking tests.
7. Keep Reviewer Lift current as facts become known: reviewed commit, finding bindings (`none` or canonical report locator + originating reviewed commit + short ID tuples), Gate owner, Gate coverage/rationale, CI evidence, local gate, red/green or N/A, changed paths, safety surfaces, decoupling proof, reviewer focus, open questions, approval authority/source, finish authority/source, and ready-push delta.
8. Run targeted checks during the implementation loop. Runtime budget/token/runtime notices do not change assigned work-item scope, child mode, or stop condition; they are runtime state, not a human stop instruction. In parent-owned gate mode, do not run/claim the final local gate; record `Gate owner: parent`, the parent-owned/not-run contract, and candidate commit, then leave the change request Draft for the parent Gate Receipt / ready transition. In builder-owned gate mode, run the full local Check Gate on the exact candidate and publish the anchor-form builder-owned Gate Receipt per [parent-owned-gate.md#builder-owned-gate-receipt](parent-owned-gate.md#builder-owned-gate-receipt), returning its read-back-verified note id in the two-line handoff. When an acceptance criterion names literal byte-for-byte wording, add targeted exact-string evidence against the current commit; do not extend that rule to ordinary prose.
9. Push the final head, verify the local and remote source commits match, update the change-request description with `forge publish`, and ensure Reviewer Lift `Reviewed SHA` equals the current provider commit the parent must gate/review.
10. Before a ready transition, use the selected `forge` provider to validate the provider-native work-item relationship/closure preview and publication readback. Fail closed on missing, incomplete, or mismatched evidence. Then use `forge act` only when the builder owns the local gate and the exact-commit ready coverage rule passes. In parent-owned gate mode, the child must not mark ready.
11. Stop after the final handoff, using the two-line contract from `../templates/builder-final-handoff.md` with `not-created` before the parent receipt exists; do not wait for the parent gate. Runtime/tool interruption or budget-notice exhaustion before that point is `failed`, not `blocked`, and never a human stop-scope blocker token such as `BLOCKED-STOP-INSTRUCTION`; reserve blocked handoffs for real work-item/workflow blockers or an explicit human-requested stop.

## Reviewer Lift child-seam rule

The Reviewer Lift block is a hard child seam: copy the selected packet's generated-copy Reviewer Lift block verbatim and fill **every** row.

- Start from the approved generated-copy block delimited by `REVIEWER-LIFT-SCHEMA:BEGIN ... REVIEWER-LIFT-SCHEMA:END` in `../templates/review-packet.md` or `../templates/review-packet-compact.md`. Copy the whole block and replace each placeholder with a verified value; a re-derived subset that silently drops rows (for example omitting `Acceptance surfaces`) is not acceptable, and fail-closed values (`none`, `N/A — <why>`) are.
- Authority rows need verifiable sources per `../templates/reviewer-lift-schema.md`. `docs/agents/check-gate.md` does not own authority policy, so it is not a valid authority source.
- Relative paths resolve against the directory of the file that contains them; run helper scripts by their resolved absolute path, never from the target's CWD. Below, `<start-build-dir>` is the absolute path of `..` and `<start-review-dir>` the absolute path of `../../start-review`. Before handoff run `node <start-build-dir>/scripts/validate-gate-receipt.mjs --mode lift-only --review-packet <packet>`: canonical full-row presence/nonempty/one-block/duplicate checks only, independent of future receipt and either owner context.
- Validate non-`none` finding tuples against all originating reports with `node <start-review-dir>/scripts/validate-finding-bindings.mjs --report <report.md> ... --lift <packet>` per `../../start-review/reference/finding-identities.md`. Bare short IDs are insufficient; native artifact/scope verification remains separate.
- Validate the work-item relationship/closure preview and published description readback through the selected `forge` provider. Missing, incomplete, or mismatched evidence blocks handoff and the ready transition.

## Post-ready push rule

If any commit is pushed after ready-marking, publish a provider-native update naming old commit → new commit, reason, changed files, gate rerun, and whether the change is substantive. Refresh `Reviewed SHA`, `CI pipeline`, and `Delta since last ready push` for the candidate handoff. In parent-owned mode return `not-created` until the new exact-commit Gate Receipt exists; identify previous receipt/review pointers as historical, preserving originating finding identities. The parent must obtain the new receipt before re-review, not before the child's pre-gate return. Silent post-ready pushes make the review binding stale.
