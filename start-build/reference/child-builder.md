# Child `mr-builder` mode

Small, self-contained path for child builders delegated by a parent orchestrator. This file is the canonical owner of the child `mr-builder` flow and intentionally excludes parent-only runtime-specific reviewer discovery details.

## Authority boundary

The launch prompt's `Gate owner` line is the **sole binding source** of the gate-ownership selection (`builder` = builder-owned gate, `parent` = parent-owned gate; when the line is absent the documented default is `builder`/builder-owned). The child must not infer gate ownership from "finish authority", forbidden-actions wording, or any other merge/finish-authority prose — those govern who may finish, not who runs the local gate, and must not influence the selection. The child echoes the literal value it read as `gate_owner_received` in its final handoff (see [../templates/builder-final-handoff.md](../templates/builder-final-handoff.md)) so the parent can verify the child bound to the explicit selection. The per-mode semantics stay owned by [parent-owned-gate.md](parent-owned-gate.md); this field only names the selection.

The child builder implements one work item and opens/maintains one Draft change request. By default it may mark ready only after the local gate is green or explicitly N/A with rationale. When parent-owned gate mode is active, the child follows the ownership contract in [parent-owned-gate.md](parent-owned-gate.md#ownership-contract): open/update the Draft change request and final handoff, do not claim gate pass/fail, and do not mark ready unless explicit parent/human delegation is recorded first. The parent orchestrator owns the mandatory review gate and any approval, finish, source-ref cleanup, or post-merge verification allowed by policy; the child must not start a reviewer, approve, finish, clean source refs, or claim the review gate is complete unless explicitly delegated.

Project-profile hooks may specialize project policy but must preserve the [Hard floors (never scaled away)](../../docs/effort-scaling.md#hard-floors-never-scaled-away).

Auxiliary project-index policy defaults to parent/coordinator ownership. Child worktrees treat index reports as read-only unless the project profile explicitly assigns index updates to the child, and child worktrees must not copy index artifacts between worktrees.

## Required reads

Load only the context needed for the work item: project rulebook index, `start-build/SAFETY.md`, this child-builder path, `parent-owned-gate.md` when parent-owned gate mode is active, `issue-pickup.md`, `../templates/reviewer-lift-schema.md`, `../templates/builder-final-handoff.md`, linked change requests, and affected docs/source/tests. Use [context and planning](context-and-planning.md) for the Discovery Budget and Build Plan Packet. Open [implementation-flow.md](implementation-flow.md) only when the compact checklist below is insufficient or when an edge case, revision, post-ready push, CI policy, or gate ambiguity requires the full common flow.

Avoid parent-orchestrator and standalone-gate detail while building: do not load parent reviewer discovery, reviewer launch protocol, finish action guidance, or post-merge verifier instructions unless the parent explicitly changes your scope.

## Absolute worktree paths for edits

The harness `edit`/`write`/`read` tools resolve RELATIVE paths against the agent **session cwd** (the coordinator checkout), not a bash shell's `cd`. A `cd <worktree>` in `bash` does NOT relocate them: a child that `cd`s into its worktree and then edits with relative paths silently lands changes in the coordinator checkout, not its worktree.

For every `edit`/`write`/`read` of a project file, use an ABSOLUTE path rooted in your worktree. Run git with `git -C <worktree>` rather than relying on shell cwd. After editing, confirm the edits landed in the worktree (`git -C <worktree> status`) and the coordinator checkout stayed clean (`git -C <coordinator> status --porcelain` empty). The parent creates the worktree and passes its absolute path; re-use that path verbatim.

## Child checklist

Credential handling discipline applies before every local shell or provider step: never `cat`, `echo`, or otherwise print token-bearing config such as `.env`, provider CLI config files, PAT stores, token env vars, or any value that may contain a secret. If an explicitly approved command must consume a credential, read it into a shell variable inside that command without printing it, pass it directly to the consuming tool, and redact diagnostics as `[REDACTED]`.

1. Run `forge preflight` and verify selected-provider transport availability, checkout/repository binding, repository locator, and default branch.
2. Resolve the supplied work item, or use the issue-pickup flow when none was supplied. Follow the canonical [issue pickup flow](issue-pickup.md), including its required description-and-current-discussion read and contradiction handling, before planning or editing.
3. Start from a clean checkout on the latest default branch: empty `git status --porcelain`, fetch origin, fast-forward the default branch, and branch from its verified remote commit using the project naming convention.
4. Write a concise Build Plan Packet before edits: intended behavior, affected surfaces, test plan, risk, non-goals, and loaded context sources with relevance.
5. Push the source branch and open one Draft change request early with `forge publish`, the provider-native work-item relationship/closure preview, a Review Packet, and the Reviewer Lift block initialized from `../templates/reviewer-lift-schema.md`. Fill `Approval authority` as `default-after-pass` with stable policy provenance unless an explicit restriction source applies. Fill the quoted `Finish authority` claim and verifiable `Finish authority source`; builders cannot grant authority.
6. Behavior-touching implementation follows TDD unless impossible or explicitly N/A with rationale in the change request. Runtime/operator/safety changes are examples of behavior-touching implementation, not a narrower TDD trigger. Exception categories require a recorded rationale and must not allow fake tests or meaningless checks. Work-item-driven work with sufficient acceptance criteria does not need a separate user-approval prompt before the first TDD slice. Missing or ambiguous behavior scope still routes back to triage with exact unanswered questions. For docs/config/mechanical work, record `TDD: N/A` rationale instead of faking tests.
7. Keep Reviewer Lift current as facts become known: reviewed commit, finding bindings (`none` or canonical report locator + originating reviewed commit + short ID tuples), Gate owner, Gate coverage/rationale, CI evidence, local gate, red/green or N/A, changed paths, safety surfaces, decoupling proof, reviewer focus, open questions, approval authority/source, finish authority/source, and ready-push delta.
8. Run targeted checks during the implementation loop. Runtime budget/token/runtime notices do not change assigned work-item scope, child mode, or stop condition; they are runtime state, not a human stop instruction. In parent-owned gate mode, do not run/claim the final local gate; record `Gate owner: parent`, the parent-owned/not-run contract, and candidate commit, then leave the change request Draft for the parent Gate Receipt / ready transition. When an acceptance criterion names literal byte-for-byte wording, add targeted exact-string evidence against the current commit; do not extend that rule to ordinary prose.
9. Push the final head, verify the local and remote source commits match, update the change-request description with `forge publish`, and ensure Reviewer Lift `Reviewed SHA` equals the current provider commit the parent must gate/review.
10. Before a ready transition, use the selected `/forge` provider to validate the provider-native work-item relationship/closure preview and publication readback. Fail closed on missing, incomplete, or mismatched evidence. Then use `forge act` only when the builder owns the local gate and the exact-commit ready coverage rule passes. In parent-owned gate mode, the child must not mark ready.
11. Stop after final handoff. Runtime/tool interruption or budget-notice exhaustion before that point is `failed`, not `blocked`, and must not be reported as a human stop-scope blocker token such as `BLOCKED-STOP-INSTRUCTION`. Reserve blocked handoffs for real work-item/workflow blockers or an explicit human-requested stop. The final handoff is the two-line contract from `../templates/builder-final-handoff.md`: the change-request locator and the durable note id (Gate Receipt note for a parent-gated builder run). Keep `validate-finding-bindings.mjs` (it validates local files the server cannot see).

## Reviewer Lift child-seam rule

The Reviewer Lift block is a hard child seam: copy the tier's generated-copy Reviewer Lift block verbatim and fill **every** row.

- Start from the approved generated-copy block in `../templates/review-packet.md` (full Review Packet) or `../templates/review-packet-compact.md` (compact packet) — the block delimited by `REVIEWER-LIFT-SCHEMA:BEGIN ... REVIEWER-LIFT-SCHEMA:END`. Do not re-derive a subset of rows from memory; copy the whole block and replace each placeholder with a verified value.
- Fill every required row from `../templates/reviewer-lift-schema.md`. Fail-closed values are fine when truly nothing applies (`none`, `N/A — <why>`); a re-derived subset that silently drops rows (for example omitting `Acceptance surfaces`) is not. A reviewer routes off the Lift as a map, and a parent must not have to delta-edit the description to restore missing rows before the ready transition.
- Quote authority rows with verifiable sources: `Approval authority` / `Approval authority source` and `Finish authority` / `Finish authority source` per the schema. `docs/agents/check-gate.md` does not own authority policy, so it is not a valid authority source.
- Lint the Lift before handoff with the pure-local presence checker `validate_reviewer_lift` (no network; reads a file or stdin). It fails closed on any missing required row per the schema. Parents may run the same helper at spot-check; it validates row presence/shape only and never judges row values.
- Before publication or handoff, validate every non-`none` `Finding bindings` tuple against all originating Review Report files with `node start-review/scripts/validate-finding-bindings.mjs --report <report.md> ... --lift <review-packet.md>` per `../../start-review/reference/finding-identities.md`. Missing, stale, ambiguous, or contradictory bindings block publication and the ready transition; a bare `MF-N`/`SF-N`/`C-N` is never sufficient.
- Before publication or handoff, use the selected `/forge` provider to validate the work-item relationship/closure preview and published description readback. Missing, incomplete, or mismatched evidence blocks handoff and the ready transition; provider-specific mechanics stay in the provider reference.

## Post-ready push rule

If any commit is pushed after ready-marking, publish a provider-native update naming old commit → new commit, reason, changed files, gate rerun, and whether the change is substantive. Before asking the parent to continue, refresh every commit-bound Reviewer Lift field so re-review starts from current evidence: `Reviewed SHA`, `CI pipeline`, `Delta since last ready push`, and, in parent-owned gate mode, a new exact-commit Gate Receipt because earlier evidence is stale. Silent post-ready pushes make the review binding stale.
