# Implementation flow

Detailed common implementation sequence for `start-build` builders. Stable compatibility anchors remain [BUILD-FLOW.md §Implementation flow](../BUILD-FLOW.md#implementation-flow), [§Check gate discovery](../BUILD-FLOW.md#check-gate-discovery), and [§Stuck protocol](../BUILD-FLOW.md#stuck-protocol). Child builders may use the smaller [child-builder path](child-builder.md) unless this full flow is needed.

## Procedure

1. Resolve the issue(s) first: supplied or via [issue pickup](issue-pickup.md). If multiple, enter [Multiple issue worktree mode](multiple-worktrees.md) and run the rest independently per worktree.
2. For a single issue, start clean from latest default branch:
   - `git status --porcelain` empty. If dirty, stop and ask — never auto-stash, reset, or clean.
   - `git fetch origin`.
   - `git checkout <default>` using `default_branch` from `gitlab` **Snippet: local-repo-preflight** when not `main`.
   - `git pull --ff-only origin <default>`. If FF fails, stop and ask; do not force.
   - Confirm `git rev-parse HEAD` matches `origin/<default>` before branching.
   - Branch using the project's naming convention; reference the issue ID.
3. Load narrow context, not the whole repo or conversation: rulebook index, issue, and affected docs/source/tests first. Expand to architecture docs, ADRs, domain docs, or `CONTEXT.md` only from evidence triggers listed in [context and planning](context-and-planning.md#discovery-budget). Record each non-obvious source and relevance reason in the Build Plan Packet or Review Packet.
4. Open **Draft MR** early targeting default branch, linked via `Closes #<id>`, after source branch exists remotely. Use `gitlab` **Snippet: draft-mr-create** with `../templates/review-packet.md` or `../templates/review-packet-compact.md` when eligible; the snippet validates description content bytes before the MCP-primary create mutation (and before any documented fallback/helper mutation), then re-reads the MR. File-backed helper/local packet wording applies only to the documented fallback/helper path, not the primary path. Do not mark ready in step. Fill **Builder** metadata `@builder — <model-id>` if exposed; omit model id instead of guessing. Initialize **Reviewer Lift** block from `../templates/reviewer-lift-schema.md`; fields may be pending, but block exists day one. Fill `Approval authority` `default-after-pass` with stable policy provenance unless an explicit restriction source applies. Fill `Merge authority` quoted finish-authority claim and `Merge authority source` verifiable provenance; builder cannot grant approval, merge, or auto-merge authority.
   - **Early Draft MR push.** This push creates the remote source branch and/or Draft MR handoff. It does not require the full local gate; use Draft status and pending/N/A Reviewer Lift values until evidence exists.
   - **Implementation pushes before ready.** Pre-ready pushes may publish incremental work or refreshed draft evidence. Run targeted checks during the red-green loop, keep Reviewer Lift current with the facts available, and do not request review from Draft state.
5. Behavior-touching implementation follows TDD unless impossible or explicitly N/A with rationale in the MR. Runtime/operator/safety changes are examples of behavior-touching implementation, not a narrower TDD trigger. Exception categories require MR rationale and must not allow fake tests or meaningless checks. Issue-driven work with sufficient acceptance criteria does not need a separate user-approval prompt before the first TDD slice. Missing or ambiguous behavior scope still routes back to triage with exact unanswered questions. Commit coherent green slices, referencing issue/slice; revision commits cite review-thread items such as `MF-1: <fix>`. For docs-only/config-only/mechanical work, state `TDD: N/A` and why in the MR — do not fake tests.
6. Use the smallest public layer that proves behavior without coupling to internals: pure unit tests for deterministic logic; adapter tests with fakes/recorded HTTP; state tests in temp dirs/throwaway DBs; orchestration tests with fake clocks verifying call ordering and calls not made; migration smoke tests; the project's full check gate before requesting review; coverage gate where required.
7. Run targeted tests during the red-green loop. Never use live product/runtime/operator external systems as regression evidence.
8. Update MR description with `gitlab` **Snippet: mr-description-update**: diff summary, acceptance-criteria evidence, safety evidence, TDD trace or `TDD: N/A` rationale, full test/check-gate output or CI link. The snippet validates description content bytes before the MCP-primary update mutation (and before any documented fallback/helper mutation), then re-reads the MR; file-backed Review Packet/helper wording applies only to the documented fallback/helper path. Keep Reviewer Lift block current as values become available. Use stable `OQ-N` IDs in body so reviewer can answer each one.
9. After the ready coverage rule below is satisfied and the Reviewer Lift names the current head SHA, lint the issue-closing keyword with the pure-local checker `validate_closes_keyword` (no network; reads a file or stdin) and fix the description if it fails closed — it rejects a description whose only `Closes #<iid>` is bolded (`**Closes:** #N`), inside a code span/fence (`` `Closes #N` ``), or missing, so a formatting-defeated keyword cannot reach ready. Then mark ready with `gitlab` **Snippet: draft-mr-mark-ready**. In parent-owned gate mode, do not mark ready here: leave the MR Draft, record the ownership contract from [parent-owned-gate.md](parent-owned-gate.md#ownership-contract), and let the parent follow the Gate Receipt seam before the ready transition. Then follow the active mode: standalone `/start-build` proceeds to [standalone gate](standalone-gate.md); child `mr-builder` stops at the documented final handoff for the parent orchestrator.
   - **Ready-marking gate.** The ready coverage rule applies only before marking ready or requesting review. It does not apply to early Draft MR creation or pre-ready implementation pushes, which stay Draft and must not request review. Run targeted checks during those Draft phases, keep Reviewer Lift current, and re-bind evidence after every push.
   - **Gate coverage classification.** Set `Gate owner` to `builder` or `parent`; set `Gate coverage` to exactly one of `full-local`, `hybrid`, or `ci-only`. Do not use `parent-owned` as coverage; parent ownership is recorded separately. `Gate coverage rationale` must cite the gate policy source, required CI mapping, local command coverage, and any unmapped CI-only jobs or `none`.
   - **Full-local coverage.** When the full local Check Gate covers every required CI job for the project profile, the builder-owned ready handoff may proceed after that exact local gate passes on the head SHA, even if exact-SHA CI is still pending or unavailable. Record the local command/result, coverage rationale, and CI status as observed.
   - **Hybrid or CI-only coverage.** When any required CI job is not covered locally, wait for exact-SHA CI success for each uncovered required job before marking ready/requesting review. Failed, canceled, skipped, missing, stale, or wrong-SHA required CI blocks ready handoff unless an authorized CI waiver is recorded in the MR and Reviewer Lift.
   - **Parent-owned gate mode.** The child records `Gate owner: parent`, the parent-owned/not-run local gate contract, and the candidate SHA only as gate evidence; the parent runs the full local gate on that exact SHA, posts the Gate Receipt, applies the same uncovered CI-only rule, and owns the Draft-to-ready transition.
   - **CI-pending review policy.** Reviewer-side approval/finish eligibility after ready is owned by the [start-review CI decision table](../../start-review/REVIEW-FLOW.md#ci-decision-table); builder readiness does not authorize approval, merge, or auto-merge.
   - **Post-ready push protocol.** If you push any commits after marking ready, post an MR comment naming old SHA → new SHA, reason, changed files, gate rerun, and whether the delta is substantive. Refresh every exact-SHA Reviewer Lift field so re-review starts from current evidence: `Reviewer Lift > Reviewed SHA`, `CI pipeline` (rebound to the new SHA), `Delta since last ready push`, and, in parent-owned gate mode, the Gate Receipt pointer — point it at a new exact-SHA Gate Receipt, since a Gate Receipt tied to an older SHA is stale evidence per [parent-owned-gate.md](parent-owned-gate.md#stale-exact-sha-evidence-fails-closed-after-a-revision-push). Use `../templates/revision-packet.md` for substantive post-ready changes, not only formal request-changes responses. The reviewer is told to refuse approval of a SHA they have not read; silently pushing after ready risks merging unreviewed commits.
   - If CI later goes red, treat it like other review feedback: fetch logs, diagnose, fix, push a commit with the post-ready delta comment. Do not unilaterally re-Draft.
10. If changes are requested, push fixes as new commits and reply to each thread. Builder replies with evidence; the reviewer resolves threads after verifying unless the project explicitly allows builder-side resolution. Update the MR description with a brief revision summary and post `../templates/revision-packet.md` as a file-backed, wrapper-validated comment via `gitlab` **Snippet: mr-note-create**. In standalone `/start-build` mode, run a **new** reviewer session per [standalone gate](standalone-gate.md). In child `mr-builder` mode, return the revision handoff; the parent orchestrator starts the fresh reviewer.

## Stuck protocol

Detailed stuck handling lives in [stuck-protocol.md](stuck-protocol.md). If blocked for more than 2 hours, keep the MR in Draft, post `../templates/stuck-packet.md` as an MR comment via `gitlab` **Snippet: mr-note-create**, apply the documented unblock label if one exists, list ranked hypotheses, and park the branch/worktree or switch only on a fresh branch/worktree.
