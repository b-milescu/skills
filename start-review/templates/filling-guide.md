# Template Filling Guide — Start Review

This guide holds instructional prose for reviewer templates. Read once per session; the templates themselves are bare skeletons.

## reviewer-final-handoff.md

- Emit this machine-readable block in `mr-reviewer` final responses after posting the GitLab Review Report and after any authorized approval/finish action attempt.
- Keep the GitLab Review Report comment as the durable review record; this block complements it as a parseable artifact for parent parsing.
- Preserve field names and top-level order. Run `bash tests/agent-handoff-templates.sh` after editing.
- Make the first fields summary-first for parent orchestration: review verdict, MR (including bound MR URL/project), reviewed SHA, pipeline, local checks, findings, approval authority, approval authority source, merge authority, merge authority source, approval action, finish action, action blocker, next action, and report URL.
- `delivery.handoff_contract` inside the final handoff must stay aligned with `review_verdict`, `approval_action`, `finish_action`, `action_blocker`, and `next_action`. Required routing fields are `phase`, `expected_next_actor`, `expected_next_action`, `blocked`, `blocker_token`, `required_parent_decision`, `safe_to_continue_without_parent`, `changed_since_last_handoff`, and non-empty `evidence_ready_for_next_actor`; use `required_parent_decision: "none"` when no parent decision is still needed, and omit `blocking_question` unless a specific actionable blocker question truly remains.
- `review_verdict` is `pass / request-changes / reject / blocked`. `pass` is a review judgment only; it never means "looks good but no approval was taken". `approval_action`, `finish_action`, and `action_blocker` say what GitLab side effects happened or why none happened.
- `mr.bound_url`, `mr.project_path`, and `mr.repo_url` record the bound MR URL/project used for commands; include host, IID, source branch, target branch, and current SHA so the parent can audit target correctness.
- Use `blocked` when guard, authority, tooling, permission, partial-review, security, or human-decision state prevents safe approval/finish: `missing-authority`, `stale-or-missing-ci`, `changed-head-sha`, `sha-bound-action-unsupported`, `preflight-failure`, `permission-failure`, `human-decision-needed`, `partial-review`, `secret-exposure-suspected`, or `other`.
- If usage limits or tooling failures stop completion before a review verdict, return prose explaining the blocker; a completed machine block should only claim verified values.
- Never include secrets, raw private payloads, or unredacted logs. For suspected secret exposure, do not quote the secret or credential, do not copy the sensitive payload, and use `[REDACTED]` plus `secret-exposure-suspected` without secret values. Use synthetic URLs/SHAs in examples.
- Consumers must tolerate absent blocks and fall back to the Review Report / human prose / Reviewer Lift.

## review-report.md

- Post as a single top-level comment on the MR with `gitlab-local` **Snippet: mr-note-create**. Use inline review comments for line-anchored findings, and reference each Must Fix item ID (MF-1, MF-2, ...) so revision commits can cite them.
- The core report is concise and summary-first: `Decision Summary`, `Context / Snapshot`, `Reviewer Lift (builder handoff)`, `Review Context Capsule`, `Findings`, `Open Questions Addressed`, `Evidence`, and `Action / Blocker`. Long checklists live in `Optional Annex: Checklists` and should stay compact.
- **Decision Summary** — First section and first screen. Draft it before final guards, then refresh it after the final MR/CI/authority snapshot and before posting. Use the same summary-first structure as the reviewer prompts: review verdict (`pass / request-changes / reject / blocked`), bound MR target, reviewed SHA, CI status/SHA, findings summary (`MF-N` / `SF-N` / `C-N` counts or IDs), local checks, Approval authority, Approval authority source, Approval action, Merge authority, Merge authority source, Finish action, Action blocker, Next action, and Report link placeholder (`this comment; final handoff contains URL when available` until GitLab exposes the comment URL). Copy these values from the final core sections instead of maintaining a second source of truth.
- **Context / Snapshot** — Compact source of truth for bound MR URL, bound MR project, explicit repo target, IID, source branch, target branch, reviewed/current SHA, CI snapshot, local check snapshot, approval authority, merge authority, reviewer identity, and report round. Duplicate critical fields only by copying from this snapshot into the Decision Summary.
- **Project binding fields** — Copy the bound MR URL/project, explicit repo target, IID, source branch, target branch, and current SHA from the final metadata snapshot. A project mismatch blocks unless the user explicitly chose a cross-repo review target. Commands that post comments, approve, merge, queue auto-merge, or close use an explicit repo target or full MR URL, never a cwd-inferred bare IID when a URL was supplied or repo inference is uncertain.
- **Reviewer Lift (builder handoff)** — Copy every field from the builder's Reviewer Lift before reading the diff. `../../start-build/templates/reviewer-lift-schema.md` owns field names, order, and required semantics; the table in this report is an approved generated copy. Treat Reviewer Lift and any Gate Receipt as maps, not truth: verify each copied value against MR metadata, diff, comments, Gate Receipt source fields, and CI before deciding, and give every safety-critical field reviewer verification and source. Treat `Approval authority` and `Merge authority` as separate builder-quoted claims, not grants; neither one is proof by itself.
- **Approval authority / Approval authority source** — Approval is allowed by default after a passing review unless explicitly restricted. Verify `Approval authority: default-after-pass` against the stable repo/rulebook policy source (for this repo, `start-review/REVIEW-FLOW.md#approval-authority-policy`) or verify the explicit restriction source before taking approval. Approval still needs normal review/CI/local-gate/OQ/SHA guards and never grants merge, auto-merge, release, deploy, close, or cleanup authority.
- **Merge authority / Merge authority source** — Both fields must be explicit and source-verified before merge/auto-merge/release/close/cleanup or other finish actions. Missing Merge authority or missing source blocks finish actions, not default approval by itself. Accepted sources include parent task prompt, human MR comment URL, rulebook path+section, or project default source. Authority source precedence: explicit human or parent instruction beats rulebook/project default; conflicts choose the most restrictive/no-action finish path. `approval-only` is valid when source-verified and means approval may proceed after normal guards, then finish stops before merge/auto-merge. `reviewer may merge`, `queue auto-merge`, and `project default: ...` without a verifiable source are blocked for finish; do not default missing merge authority to approval-only and record `Action blocker: missing-authority` for the finish blocker.
- **Review Context Capsule** — Fill repo, MR, authority, CI, scope, artifacts, and context-expansion rows with Claim / Reviewer verification / Source values. Parent/builder reasoning, Reviewer Lift rows, local handoff files, and prior session notes stay claims until verified from Tier 1 or risk-triggered Tier 2 evidence. Record any Tier 3 broad context use with its human instruction or concrete necessity. Safety-critical verification/source is required before any pass verdict or GitLab action.
- **Findings** — Required but concise. Use stable IDs (`MF-N`, `SF-N`, `C-N`) only for real findings. Each Must Fix must be revision-ready: exact path + line/range locator, concrete problem, and bounded remedy direction. Prefix credential/security findings with `[SECURITY]`. For suspected credential exposure, safe wording is `[SECURITY] Potential secret exposure at path:line; value [REDACTED]`; do not quote or copy the secret payload. If a human/product/security decision is still required, keep it in `blocked` / `human-decision-needed` routing instead of inventing an MF item or pretending it is builder work. If a bucket has no findings, write an explicit verifier-safe sentence such as `No MF findings after diff, evidence, and safety review.`
- **Open Questions Addressed** — Required. Classify every `OQ-N` from the MR description with `../REVIEW-FLOW.md` [CI and Open Question decision tables](../REVIEW-FLOW.md#ci-and-open-question-decision-tables). Replace the fill instruction with one subsection or bullet per OQ. If no OQ exists after verification, write `Verified: no OQ-N entries in the MR description after review.` Do not leave hardcoded completion placeholders.
- **Evidence** — Required evidence hub. Summarize builder evidence accepted/rejected, CI status/SHA, Gate Receipt verification when parent-owned gate mode was used, reviewer-run commands, acceptance criteria checked, TDD / behavior-test evidence, structural maintainability sweep, Reviewer Focus sweep, and Code I Ran. Keep it short; move verbose safety/state/external-system inventories into the annex.
- **Tests / CI / Local Checks** — Builder evidence accepted/rejected; tests you ran; CI status; Gate Receipt local-gate verification when present. Classify CI with `../REVIEW-FLOW.md` [CI and Open Question decision tables](../REVIEW-FLOW.md#ci-and-open-question-decision-tables), then note how approval authority and merge authority sources were verified or why either one blocked the affected action.
- **Acceptance Criteria Evidence Checked** — For each acceptance criterion from the MR/issue, state accepted evidence or gap.
- **TDD / Behavior-Test Evidence** — Behavior-touching MR: public interface tested? `RED`/`GREEN` trace present or reasonably N/A? Tests avoid implementation coupling? Non-behavior MR: state why TDD is not applicable.
- **Structural Maintainability Sweep** — Summarize the bounded diff-first pass from `REVIEW-FLOW.md`: code-judo simplification, spaghetti/special-case branching, wrappers/abstractions, wrong-layer or duplicate helpers, type-boundary issues, orchestration complexity, and the `<1000` -> `>1000` file threshold. Record blocker-level regressions as `MF-N`; use `C-N` only for non-blocking or broader follow-up quality work; do not block on style-only preferences.
- **Reviewer Focus Sweep** — What the builder flagged in Reviewer Lift > Reviewer Focus, and what you found when you read those areas first. Use `None flagged` only when that is verified from Reviewer Lift.
- **Code I Ran** — Record checkout path and checkout SHA used for local checks before listing commands. If no local execution ran, state `Not run — <rationale>`. Never paste secrets or run mutating product/runtime/operator commands.
- **Action / Blocker** — Repeat the `Review verdict` and the separate action fields. `pass` means the review judgment passed; it does not imply GitLab approval, merge, or auto-merge. `blocked` is for non-code-review blockers that prevent safe approval/finish. If a final snapshot guard fails before posting, convert the report to `blocked`; if an action failure happens after a pass verdict is posted, keep the pass judgment but record the failed action and blocker in the final handoff and, when useful for MR history, an action-result note.
- **Approval action** — Record only GitLab approval side effects: intended approve, approved, not-approved, blocked, or N/A. Use `intended: approve` in the posted report when approval will be attempted after posting; use `approved` only in an action-result note/final handoff after SHA-bound approval and confirmation evidence. Do not use a passing review verdict as a substitute for approval evidence.
- **Finish action** — Record only GitLab finish side effects: intended direct merge, intended queue auto-merge, merged, auto-merge queued, approval-only stop, human-release stop, none, blocked, or N/A. Use intended action values in the posted report for post-report finish attempts; use completed action values only after the SHA-guarded direct merge or auto-merge queue action is verified.
- **Action blocker** — Use `none` or a stable token: `missing-authority`, `stale-or-missing-ci`, `changed-head-sha`, `sha-bound-action-unsupported`, `preflight-failure`, `permission-failure`, `human-decision-needed`, `partial-review`, `secret-exposure-suspected`, or `other`.
- **Next action** — Tell the parent orchestrator how to route: finish-by-authorized-actor, revise, human-escalation, wait-ci, rerun-review, or fix-blocker. Keep this equal to `delivery.handoff_contract.expected_next_action`; human-decision blockers should also fill `required_parent_decision` and use `blocking_question` only for a specific actionable question.
- **Optional Annex: Checklists** — Optional compact evidence for safety/state/external-system surfaces. Fill only rows that add evidence beyond the core report. The safety checklist covers domain envelope, product/runtime/operator external-system mutations, approved adapters, observe/enforce or dry-run/production gates, protective sequencing, coordination primitives, immutable baselines, exact-decimal math, and pure engines. The state checklist covers typed models, atomic writes, append-only migrations, transactional events, CLI/interop contracts. The external-system/credential checklist covers no live mutation, adapter-only calls, fake/recorded HTTP tests, redaction, and secrets untouched.
- **Evidence-Backed Positive Patterns** — Optional. Call out good work only when specific, evidence-backed, and useful to reinforce. Do not force praise or invent positive feedback.
- **Architectural Observations** — Optional broader patterns, ADR suggestions, or rejection rationale.
- **Follow-ups for Other Tasks** — Items not blocking this MR. Open separate issues and link them when a `C-N` or other non-blocking finding should survive after merge. Record brief-quality defects here too when the issue brief omitted critical context, acceptance criteria, test strategy, or non-goals; name the missing fields and the avoidable discovery or rework. Use only the documented GitLab/local issue workflow and live label vocabulary.
- **Final Notes** — Short parent/human routing note only when it is not already covered above.

## unblock-response.md

- Use when responding to a Stuck Packet. Post as an MR comment with `gitlab-local` **Snippet: mr-note-create**. When Builder resumes, remove the project's unblock label if one exists.
- **Summary** — One paragraph: your read and the recommended direction.
- **Engagement with hypotheses** — Respond to each ranked hypothesis (`H-N`) the builder listed in the Stuck Packet, one subsection per hypothesis: confirm, refute, refine, or defer it with the evidence or check that backs your call.
- **Direction** — Pointer / correction / pair / escalation. Cite files, tests, docs, or commands.
- **Safety notes** — Any product/runtime/operator external-system / credential / state precautions before continuing.
- **What I did not check** — Honest scope.
- **Confidence** — High / medium / low and why.
