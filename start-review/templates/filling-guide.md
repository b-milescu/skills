# Template Filling Guide — Start Review

This guide holds instructional prose for reviewer templates. Read once per session; the templates themselves are bare skeletons.

## reviewer-final-handoff.md

- Emit the two-line contract in `mr-reviewer` final responses after posting the durable Review Report and after any authorized approval/finish action attempt: change-request locator and Review Report note id.
- Keep the durable Review Report as the immutable review record. Parents read `forge snapshot` `bindings` / `claims` and discover later action explanations via native notes/discussions under [Post-report action evidence](../REVIEW-FLOW.md#post-report-action-evidence), not YAML or future links in the report.
- Run `bash tests/agent-handoff-templates.sh` after editing.
- Keep judgment, target/commit, evidence, findings, intended/no-action state, and publication-time blocker/routing in the durable Review Report, not extra final-response fields. Later outcomes and routing belong in the actor's backlinking action note.
- Review verdict is `pass / request-changes / reject / blocked`. `pass` records a complete valid review independently of whether approval or finish is permitted or taken; completed side effects require native post-read and the separate action record.
- Classify failed predicates using [Approval-authority policy](../REVIEW-FLOW.md#approval-authority-policy), not blocker names alone. Use review verdict `blocked` when review validity cannot be established; incomplete coverage, wrong repository, stale head before publication, invalid required gate evidence, and compromised independence still prevent pass. Action-only missing authority/permission or unsupported action binding retains a complete current review's judgment while denying the affected action with the canonical blocker and next actor/action. A builder evidence gap may instead require `request-changes` and `revise`; CI is advisory.
- `blocker_detail` is optional unless `action_blocker` is `other`; then it must be a non-empty one-line explanation of the unlisted blocker.
- If tooling failure stops report completion, return prose identifying the actual blocker; do not invent a report note ID.
- Never include secrets, raw private payloads, or unredacted logs. For suspected secret exposure, do not quote the secret or credential, do not copy the sensitive payload, and use `[REDACTED]` plus `secret-exposure-suspected` without secret values. Use synthetic URLs/SHAs in examples.
- Consumers must tolerate absent blocks and fall back to the Review Report / human prose / Reviewer Lift.

## review-report.md

- Post a single top-level **plain, non-resolvable note** on the change request through provider-native `forge publish`. Validate the full Review Report body with safe body validation or the safe note tool's embedded Safe GitLab Text validation before posting; use safe publication rather than unsafe raw inline bodies. Apply [Findings and tone](../REVIEW-FLOW.md#findings-and-tone) to optional comments and existing threads, including accidentally resolvable reports. Line-anchored requirement comments cite their finding tuple or `OQ-N`; optional `SF-N`/`C-N` findings stay in the report or an explicitly non-blocking comment lifecycle.
  After posting, read back published Review Report artifact verify body matches source report file/content before treating Review Report durable/posted. Placeholder, partial, literal-expansion, body-mismatch notes fail closed: repost through safe-body-validated note posting or record transport blocker; do not approve or finish based on non-durable report.
- The core report is concise and summary-first: `Decision Summary`, `Context / Snapshot`, `Finding identities`, `Reviewer Lift (builder handoff)`, `Review Context Capsule`, `Findings`, `Open Questions Addressed`, `Evidence`, and `Action / Blocker`. Long checklists live in `Optional Annex: Checklists` and should stay compact.
- **Decision Summary** — First section and first screen. Draft before final guards, then refresh after the final change-request/CI/authority snapshot and before posting. Copy review verdict, change-request locator, repository, reviewed commit, CI, findings, local checks, authority/actions, blocker, next action, and report locator from the core sections. Keep `Reviewed commit` and `Findings summary` bare per `../reference/finding-identities.md`: one value per cell, every finding by ID, and commentary in a neighbouring cell or the report body — trailing prose there silently drops the machine reviewed-SHA and finding claims.
- **Context / Snapshot** — Compact source of truth for the change-request identifier/locator, canonical repository/default branch, source/target, current/reviewed commit, CI, local checks, authority, reviewer, and report round.
- **Binding fields** — Follow `../REVIEW-FLOW.md` [Binding and completeness](../REVIEW-FLOW.md#binding-and-completeness) for provider and commit binding. After publication, a changed head records `changed-head-sha` and `rerun-review` in action output; preserve the report's historical reviewed commit, judgment, and finding identities rather than rebinding them to the new head.
- **Finding identities** — Follow `../reference/finding-identities.md`. Choose one stable report locator before publication, bind it and the exact reviewed SHA to every real `MF-N`/`SF-N`/`C-N` in the marked table, then run `node start-review/scripts/validate-finding-bindings.mjs --report <this-report.md>`. The posted comment URL is separate `report_url`; never use `pending` as the canonical locator.
- **Reviewer Lift (builder handoff)** — Copy every field from the builder's Reviewer Lift before reading the diff. `../../start-build/templates/reviewer-lift-schema.md` owns field names, order, and required semantics; the table in this report is an approved generated copy. Treat Reviewer Lift and any Gate Receipt as maps, not proof: verify each copied value against change request metadata, diff, comments, Gate Receipt source fields, and advisory CI before deciding, and give every safety-critical field reviewer verification and source. Verify `Gate owner`, `Gate coverage`, `Gate coverage rationale`, and the exact-candidate Gate Receipt as quality-gate evidence; classify CI only as an advisory observation per `../REVIEW-FLOW.md` [CI and Open Question decision tables](../REVIEW-FLOW.md#ci-and-open-question-decision-tables).
- **Approval authority / Approval authority source** — Follow `../REVIEW-FLOW.md` [Approval-authority policy](../REVIEW-FLOW.md#approval-authority-policy); record `Approval authority: default-after-pass` and its verified source, or the stronger restriction.
- **Finish authority / Finish authority source** — Follow `../REVIEW-FLOW.md` [Finish authority source precedence](../REVIEW-FLOW.md#finish-authority-source-precedence) and [Approval-authority policy](../REVIEW-FLOW.md#approval-authority-policy) for the explicit Finish claim and verified source.
- **Review Context Capsule** — Follow `../REVIEW-FLOW.md` [Review Context Capsule](../REVIEW-FLOW.md#review-context-capsule) for claim, verification, source, and evidence-tier rules.
- **Findings** — Follow `../REVIEW-FLOW.md` [Findings and tone](../REVIEW-FLOW.md#findings-and-tone) and `../reference/finding-identities.md`; keep each finding revision-ready with its `(Report locator, Reviewed SHA, Finding ID)`, include a bounded remedy direction, and write an explicit verifier-safe sentence for an empty bucket.
- **Open Questions Addressed** — Apply `../REVIEW-FLOW.md` [CI and Open Question decision tables](../REVIEW-FLOW.md#ci-and-open-question-decision-tables) to each `OQ-N`; if none exist, write `Verified: no OQ-N entries in the change request description after review.`
- **Evidence** — Required evidence hub. Summarize builder evidence accepted/rejected, CI status/commit, Gate Receipt verification when parent-owned gate mode was used, reviewer-run commands, acceptance criteria checked, TDD / behavior-test evidence, structural maintainability sweep, Reviewer Focus sweep, and Code I Ran. Keep it short; move verbose safety/state/external-system inventories into the annex.
- **Tests / CI / Local Checks** — Apply `../REVIEW-FLOW.md` [CI and Open Question decision tables](../REVIEW-FLOW.md#ci-and-open-question-decision-tables), then record accepted or rejected builder evidence, reviewer checks, CI, Gate Receipt evidence, and authority-source verification.
- **Acceptance Criteria Evidence Checked** — For each acceptance criterion from the change request/issue, state accepted evidence or gap. **AC artifact-naming rule:** when an AC names a produced evidence artifact (tabulated diff, recorded identification, note posted at a named location, or any other deliverable at a specific path or comment), the AC is satisfied only by that artifact existing at the named location; prior-work references, indirect validation, or plausibility arguments do not satisfy it. Record the artifact location verified or the gap if the artifact is absent.
- **TDD / Behavior-Test Evidence** — Behavior-touching change request: public interface tested? `RED`/`GREEN` trace present or reasonably N/A? Tests avoid implementation coupling? Non-behavior change request: state why TDD is not applicable.
- **Structural Maintainability Sweep** — Apply `../REVIEW-FLOW.md` [Structural maintainability sweep](../REVIEW-FLOW.md#structural-maintainability-sweep) and record any `MF-N` or `C-N` outcomes.
- **Reviewer Focus Sweep** — What the builder flagged in Reviewer Lift > Reviewer Focus, and what you found when you read those areas first. Use `None flagged` only when that is verified from Reviewer Lift.
- **Code I Ran** — Record the isolated checkout path and observed commit used for local checks, and confirm it matches the reviewed commit before listing commands. If no local execution ran, state `Not run — <rationale>`. Never paste secrets or run mutating product/runtime/operator commands.
- In `Finish owner: parent` mode, apply `../REVIEW-FLOW.md` [Approval-authority policy](../REVIEW-FLOW.md#approval-authority-policy): valid review returns approval `not-approved`, finish `none`, blocker `none`, and `finish-by-authorized-actor` to the parent. This intentional no-action route does not manufacture `missing-authority` or waive review-validity predicates.
- **Action / Blocker** — Follow `../REVIEW-FLOW.md` [Publication and actions](../REVIEW-FLOW.md#publication-and-actions); keep verdict, approval, finish, blocker, and next actor/action separate. An action-only failure before or after publication does not change a valid judgment; a review-invalidating failure still prevents pass. For a `request-changes` verdict, record `Approval action: not-approved`, `Finish action: none`, `Action blocker: none`, and `Next action: revise`.
- **Approval action** — Record intended approval or no-action state in the pre-action report. Verified effects belong to [Post-report action evidence](../REVIEW-FLOW.md#post-report-action-evidence).
- **Finish owner** — Record the launch-supplied owner and apply `../REVIEW-FLOW.md` [Approval-authority policy](../REVIEW-FLOW.md#approval-authority-policy).
- **Finish action** — Record intended finish or no-action state in the pre-action report; the authorized actor owns native post-read and any required later action note. Parent-owned reviewers return without acting or waiting for that note.
- **Action blocker** — Use `none` or a stable token: `missing-authority`, `changed-head-sha`, `merge-conflict`, `sha-bound-action-unsupported`, `preflight-failure`, `permission-failure`, `human-decision-needed`, `partial-review`, `secret-exposure-suspected`, or `other`. CI status is not a blocker. Use `other` only for a blocker no listed token names, and add a one-line reason in **Action / Blocker**. Canonical values are owned by [`handoff-tokens.schema.json`](../reference/handoff-tokens.schema.json).
- **Next action** — Follow [Publication and actions](../REVIEW-FLOW.md#publication-and-actions). A separate supported compact delivery index reflects the latest verified routing (including a later action note), without rewriting the original report; the two-line final requires no such block.
- **Optional Annex: Checklists** — Optional compact evidence for safety/state/external-system surfaces. Fill only rows that add evidence beyond the core report. The safety checklist covers domain envelope, product/runtime/operator external-system mutations, approved adapters, observe/enforce or dry-run/production gates, protective sequencing, coordination primitives, immutable baselines, exact-decimal math, and pure engines. The state checklist covers typed models, atomic writes, append-only migrations, transactional events, CLI/interop contracts. The external-system/credential checklist covers no live mutation, adapter-only calls, fake/recorded HTTP tests, redaction, and secrets untouched.
- **Evidence-Backed Positive Patterns** — Optional. Call out good work only when specific, evidence-backed, and useful to reinforce. Do not force praise or invent positive feedback.
- **Architectural Observations** — Optional broader patterns, ADR suggestions, or rejection rationale.
- **Follow-ups for Other Tasks** — Items not blocking this change request. Open separate issues and link them when a `C-N` or other non-blocking finding should survive after merge. Record brief-quality defects here too when the issue brief omitted critical context, acceptance criteria, test strategy, or non-goals; name the missing fields and the avoidable discovery or rework. Use only the documented provider/local issue workflow and live label vocabulary.
- **Final Notes** — Short parent/human routing note only when it is not already covered above.

## unblock-response.md

- Use when responding to a Stuck Packet. Post as an change request comment with `forge publish`. When Builder resumes, remove the project's unblock label if one exists.
- **Summary** — One paragraph: your read and the recommended direction.
- **Engagement with hypotheses** — Respond to each ranked hypothesis (`H-N`) the builder listed in the Stuck Packet, one subsection per hypothesis: confirm, refute, refine, or defer it with the evidence or check that backs your call.
- **Direction** — Pointer / correction / pair / escalation. Cite files, tests, docs, or commands.
- **Safety notes** — Any product/runtime/operator external-system / credential / state precautions before continuing.
- **What I did not check** — Honest scope.
- **Confidence** — High / medium / low and why.
